# Re-derivability: what it takes to check a decision record without running the producer's code

Generated by `python3 experiments/rederivability/measure.py`. Every figure below is the output of a
command run by that script; `tests/test_rederive.py` re-runs it and refuses on drift. No figure here
is written by hand.

## The roof, stated first

No rung of the ladder below removes the need to trust that the retained inputs are what the system
actually saw at decision time. That is the execution seam. It is outside this measurement and it
bounds every result in it. Forgery F5 is in the table for exactly this reason: it is a record whose
every check in this repository passes, including independent re-derivation, and whose account of one
call is false. A format claiming more than this is claiming something no amount of recomputation
can supply.

## The ladder, as the measurement left it

Four rungs were proposed. The measurement kept the shape and changed what decides a placement, because
the ranking by *engine* turned out not to predict the ranking by *re-derivability*:

| rung | what a verifier does | what it still accepts on trust |
|---|---|---|
| **L0** | executes the producer's decider (`dr.verify --replay`) | the decider module is the one that decided; everything above |
| **L1** | drives the published engine on a request the record retains | every step that built that request |
| **L2** | rebuilds the request from the retained inputs and the published specification, then drives the engine | that the specification is complete; the retained inputs |
| **L3** | as L2, with the inputs independently attested | the attester; the execution seam |

**What the measurement changed.** A rung is not decided by whether the grammar has a published engine.
It is decided by whether the *function from retained input to engine request* is published. Those come
apart in both directions, and both directions were measured below.

## 1. The Cedar records: re-derived, with no producer code in the path

`tools/rederive.py` installs a meta-path finder that raises on `emitters.*`, `dr.verify` and `dr.emit`
before importing any engine, and refuses to run if the producer's code is importable. The
demonstration is a test, not an assertion
(`tests/test_rederive.py::test_the_producer_emitter_cannot_be_imported_on_this_path`).

| record | rows | outcome agree | reason agree | reason unknown (vocabulary) | reason differ | rows the rebuild changed |
|---|---:|---:|---:|---:|---:|---:|
| `toolcalls-canonical` | 40 | 40 | 40 | 0 | 0 | 11 |
| `toolcalls-store` | 40 | 40 | 40 | 0 | 0 | 0 |
| `toolcalls-caller` | 40 | 40 | 40 | 0 | 0 | 0 |

Every row re-derives. That figure on its own is worth little: the rebuild in `tools/rederive.py` was
written by the same hand as the emitter, so agreement shows the two readings coincide and not that the
specification determines them. The honest measurement is the assumption ledger and the instrument check
below.

### The assumptions the rebuild required

`SPEC.md` names `url-v1` and lists all 8 of its canonicalised keys, so the
assumptions below are no longer guesses about undocumented behaviour. They remain assumptions
because a specification is not the artefact a verifier holds: the policy object carries the
mode's name and not its content, so nothing in a signed record binds it to the text above. Each
entry says what the rebuild had to take on trust and what would make the record carry it.

- **A1 — which context keys the url-v1 mode applies to, and which operation each receives.** Why it was needed: when this was measured SPEC.md did not mention url-v1 at all and the map existed only as a variable name in emitters/cedar.py's docstring; SPEC.md §8 has listed the keys and their operations since 24 October 2026. The policy object still carries the mode's name and not its content, so the map is published and no digest covers it. Assumed: host-kind: host, name, domain, recipient_domain; path-kind: url_path, path; upper: currency; lower: scheme — inferred from the key names and the prose Removed by: carrying the key map in the policy object (canonical_keys), so the digest covers it.
- **A2 — that entity ids are canonicalised only for entity types whose name ends in 'Host'.** Why it was needed: stated in the emitter's docstring and, since 24 October 2026, in SPEC.md §8; the suffix test remains a producer convention and the policy object does not say which types carry host-shaped ids Assumed: principal and resource only, type name ending in 'Host', using the host operation Removed by: declaring the canonicalised entity types in the policy object.
- **A3 — which keys of the retained input are part of the engine request.** Why it was needed: the retained input carries keys the request does not (kind, note, entities); until SPEC.md §8 declared the request shape on 24 October 2026 no published text said which were decision inputs and which were commentary, and the record itself still does not Assumed: principal, action, resource and context form the request; entities is the caller-asserted entity set; kind and note are commentary and are dropped Removed by: retaining the constructed request beside the raw input, or declaring the request shape.
- **A4 — the exact host and path operations.** Why it was needed: the docstring says 'lower-cases and IDNA-encodes', 'strips a trailing dot', 'normalises . and .. after percent-decoding'; SPEC.md §8 has fixed the order, the leading slash and the encoding-failure fallback since 24 October 2026, by description and not by reference to a standard Assumed: strip whitespace, strip trailing dots, lower-case, then Python's 'idna' codec, falling back to the lower-cased form on UnicodeError; percent-decode once then posixpath.normpath, re-attaching a leading slash when the input had one Removed by: specifying the operations by reference to a standard (RFC 5891 for IDNA, RFC 3986 §6 for paths).
- **A6 — for a conformance record, how a corpus test file becomes an engine request.** Why it was needed: the record's retained input is a pointer ({test, request}), not an input. The decision inputs live in the corpus, which the policy names by per-file digest but does not carry. Nothing published says how a test file's fields become a request, which policy/schema format each extension implies, or which file of the test supplies the entities Assumed: the test JSON's requests[i] gives principal, action, resource and context directly; policies are Cedar text unless the filename ends .json/.cedarjson; the schema is JSON when it ends .json and Cedar schema text otherwise; entities come from the test's entities file Removed by: retaining the constructed request per row, or carrying the corpus in the record.
- **A5 — how the reason string is derived from the engine's diagnostics.** Why it was needed: the emitter's docstring describes it, and SPEC.md §8 has defined it for this grammar since 24 October 2026; before that the replay section said the comparison was on (outcome, reason) without saying how a reason is formed Assumed: sorted determining policy ids joined with '+'; 'allow' when ALLOW with none; 'no-policy-permits' when DENY with none; 'request-invalid' when the engine refuses the request Removed by: defining the reason derivation in the specification, per grammar.

## 2. How many rows each producer-side step actually changed

A step that alters nothing on real data leaves those rows soundly re-derivable. These are counts of
rows the step changed, per record.

| step | `toolcalls-canonical` | `toolcalls-store` | `toolcalls-caller` |
|---|---:|---:|---:|
| host | 5 of 40 | 0 of 40 | 0 of 40 |
| path | 3 of 40 | 0 of 40 | 0 of 40 |
| upper | 1 of 40 | 0 of 40 | 0 of 40 |
| lower | 2 of 40 | 0 of 40 | 0 of 40 |
| entity_id_host | 3 of 40 | 0 of 40 | 0 of 40 |
| dropped_keys | 40 of 40 | 40 of 40 | 40 of 40 |
| entity_source_substitution | 40 of 40 | 40 of 40 | 0 of 40 |

The canonicalisation steps touch 11 of 40 rows in total on the canonical setting and none at all on
the other two, whose mode is `none`. Two steps touch every row of every record: the request shape
drops keys the retained input carries (`kind`, `note`), and the policy's entity source overrides the
entities the caller asserted. Both are unconditional, so no row of any Cedar record here is free of
producer-side reshaping, even where the canonicalisation is off.

## 3. The second body of data: Cedar's conformance corpus as a record

The 40 tool calls and the 2,400-row conformance sample fail differently, and the difference is the
result. The conformance record's retained input is not an input: it is a pointer,
`{"test": "corpus-tests/<file>.json", "request": 0}`. The decision inputs — policy text, schema,
entities, the request itself — are in the corpus, which the policy names by per-file digest and does
not carry.

```
$ python3 tools/rederive.py examples/cedar/out/conformance-drt-sample
the record's policy names its corpus as $CEDAR_DRT_ROOT and does not carry it; set CEDAR_DRT_ROOT to a checkout whose files match the 1200+ digests in the policy
```

With the corpus obtained out of band, the digests then establish that the one in hand is the one the
record was made against, and every row re-derives:

| | |
|---|---:|
| rows | 2400 |
| outcome agree | 2400 |
| reason agree | 2400 |
| reason differ | 0 |
| assumptions required | A6, A5 |
| corpus | corpus resolved from $CEDAR_DRT_ROOT, all 1200 named file digests match |

So the conformance record needs **two** assumptions where the tool-call records need **five** — it has
no canonicalisation step at all — and in exchange it does not carry its own decision inputs, so a
verifier must fetch 11,354 files before the first row can be checked. The tool-call record is
self-contained and under-specified; the conformance record is fully specified about everything it
contains and contains a reference instead of the inputs. Neither is strictly higher on the ladder
than the other, which is why the rung has to be reported per field rather than per record.

## 4. A decider with no published engine

`toolgate` has no published engine and no published decision function: its policy object is a
tool-to-argument-type table and the whole of the decision is in `emitters/toolgate.py`. `SPEC.md`
says nothing about it. `experiments/rederivability/naive_toolgate.py` is an independent
reimplementation written from the policy object alone, before reading that module's `decide()`.

| record | rows | outcome agree | reason agree | divergence kinds | guesses required |
|---|---:|---:|---:|---|---:|
| `toolgate-benchmark` | 12 | 12 | 8 | {'arg_type vs type': 2, 'arg_undeclared vs undeclared': 1, 'arg_missing vs missing': 1} | 6 |
| `toolgate-production` | 40 | 40 | 29 | {'arg_undeclared vs undeclared': 5, 'arg_type vs type': 6} | 6 |

**Every outcome re-derives, from the policy object alone, with no published engine and no published
decision function.** The reason diverges on the prefix vocabulary only — `arg_type:` against `type:`,
`arg_missing:` against `missing:` — which is a naming difference of the kind that should be
reported `unknown` rather than `failed`. So the decider with no engine reaches outcome-level L2, and
the Cedar decider with a published engine and published semantics reaches the same rung while needing
five assumptions, one of which changes outcomes when guessed wrong. A published engine is not what
makes re-derivation possible; a small enough policy object that nearly *is* the decision function is.

## 5. The instrument check

A tool that agreed with the records no matter what it did would report the same figures. Removing one
entry from the assumed key map (A1) — forgetting that `url_path` and `path` take the path operation, a
plausible guess from the key names alone — moves the result:

```
as written:       outcome agree 40/40, reason differ 0
A1 missing paths: outcome agree 38/40, reason differ 3
  seq 29: row ['DENY', 'no-policy-permits'] -> rederived ['ALLOW', 'policy3']
  seq 30: row ['ALLOW', 'policy3'] -> rederived ['DENY', 'policy5']
```

The dangerous direction is the one that appears: on seq 29 the record says DENY for
`/workspace/%2e%2e/etc/passwd` and an implementer who guessed A1 wrong derives ALLOW. A wrong guess
about an unspecified pre-processing step does not merely fail to re-derive; it re-derives a permit the
policy refuses.

## 6. The forgeries, and which check catches which

Five records, each signed with a test key generated from a fixed label by
`experiments/rederivability/forge.py` (no production key is read). F1–F4 are made by tampered copies
of the Cedar decider under `experiments/rederivability/tampered/`, each changing exactly one
producer-side step. Each tampered module keeps `DECIDER_ID` and `DECIDER_VERSION` identical to the
honest module, because the version string names the engine (`cedarpy-<release>`) and says nothing
about the wrapper that builds the request. F5 changes no code at all.

| forgery | what it misreports | `replay` under the producer's own module | `replay` under the honest module | independent re-derivation |
|---|---|---|---|---|
| `f1-canonicalisation-widened` | the host operation folds confusable characters, so a lookalike host becomes the allow-listed one | replay established, ESTABLISHED | replay failed, FAILED | **caught** (1 outcome) |
| `f2-context-key-dropped` | request construction removes a context key the policy reads | replay established, ESTABLISHED | replay failed, FAILED | **caught** (3 outcome) |
| `f3-reason-relabelled` | the reason names a forbid that did not fire | replay established, ESTABLISHED | replay failed, FAILED | **caught** (23 reason) |
| `f4-entity-source-swapped` | the policy declares the store; the producer evaluates with the caller's entities | replay established, ESTABLISHED | replay failed, FAILED | **caught** (3 outcome) |
| `f5-input-fabricated` | the retained input of seq 24 is a benign call the agent never made; the decision is honestly computed from it | replay established, ESTABLISHED | replay established, ESTABLISHED | passes |

**`f5-input-fabricated` passes every check in this repository.** The retained input of seq 24 is a benign call the agent never made; the decision is honestly computed from it. The chain
re-derives, the counts derive from the rows, the decider signed every row at decision time, the
retained input's digest matches the row that cites it, and driving the published engine on that
input reproduces the recorded decision exactly. The record is a sound account of a decision
correctly taken on an input the agent never supplied. This is the roof, demonstrated rather than
asserted, and no rung above L2 is reachable without an attester outside the producer.

It is the one forgery published as an artefact rather than as a recipe, because a reader who runs
the four that fail and never reaches the one that passes leaves thinking the gap is closed:

```
$ python3 -m dr.verify experiments/rederivability/out/f5-input-fabricated --registry experiments/rederivability/out/registry.json --decider-registry experiments/rederivability/out/deciders.json
experiments/rederivability/out/f5-input-fabricated

  OK      document       format_version 1 shape, and payload_hash recomputes from the canonical payload
  OK      signing_trust  key 'rederivability-test-producer' is active in the registry
  OK      signature      the signature verifies over the payload
  OK      chain          40 rows re-derive from GENESIS to the signed terminal hash
  OK      decisions      40 rows written, by outcome {'ALLOW': 17, 'DENY': 23}, one decider, 1 policy; a count of what the producer wrote, not of what happened
  OK      profile        the rows support the declared profile 'production'
  n/a     correctness    the production profile carries no correctness property: the rows have no labels and the record claims none
  OK      retained       3 retained file(s) present with their digests, inputs match the rows, policy matches the rows
  n/a     replay         not requested; pass --replay <decider module> to re-decide the retained inputs
  OK      invocation     every one of the 40 rows carries a decision the decider signed under ['rederivability-test-decider'] at decision time, bound to this record and sequence; the producer could not have written these rows without the decider
  n/a     stream         the record is not part of a stream
  n/a     completeness   not claimed and not establishable: the 40 rows are what the producer wrote, and nothing in a self-signed record bounds what it did not write. A receipt (--receipt) for a decision the record lacks refutes it
  n/a     receipts       no receipts supplied
  n/a     witness        no witness statement supplied; a record witnesses nothing about itself

VERDICT: ESTABLISHED
$ echo $?
0
```

What the table shows about the first four: each is caught by replay under the *honest* module and by
independent re-derivation, and none is caught by replay under the module the producer supplies. Since
the record's decider string is identical in both cases, nothing in the record tells a verifier which
module it was handed. That is the gap re-derivation closes: it replaces *a* module with *the
specification plus a published engine*, and it is the only one of the three checks that does not
require the verifier to already possess an honest copy of the producer's code.

## 7. What re-derivation establishes that `replay` and `invocation` do not

- That the decision follows from the retained policy and the retained input under the grammar's
  published semantics, with no producer code consulted — so a tampered wrapper shipped alongside the
  record cannot vouch for itself (F1, F2, F4).
- That the reason attributes the decision to the policies the engine actually determined it by (F3).
- That the pre-processing a record depends on is or is not written down: the assumption ledger is a
  per-format measurement, and this format currently scores five on Cedar.

### And what it still does not, in the same detail

- **That the retained input is what the system saw.** F5. The seam is unaddressed and unaddressable
  from inside the record.
- **That the retained policy is the policy the deployment enforced.** The digest binds the policy to
  the record, not to the running system. A producer who records a stricter policy than it runs produces
  a record that re-derives perfectly.
- **That the decider was consulted at all.** Re-derivation shows what the policy requires; it is
  indifferent to whether anything ran. `invocation` (SPEC §15) is what addresses that, and the two are
  complements rather than substitutes: re-derivation without attestations cannot tell a gate from a
  forwarder, and attestations without re-derivation cannot tell an honest gate from a tampered one.
- **That the rows are all the rows.** Unchanged by any of this; `completeness` is still never
  established from the producer's record alone.
- **That the engine the verifier drives agrees with the engine the producer drove.** Re-derivation
  substitutes the verifier's engine release. Engine drift is measured separately (`ENGINES.md`,
  `LEAN.md`) and the established-version mechanism is what carries a claim across releases.

## 8. Per-field placement

Per field of the Cedar decision input, what the record retains and what a reader can rebuild:

| field | retained as | rebuildable from record + published spec? | rung |
|---|---|---|---|
| `principal.type`, `action`, `resource.type` | raw, used as given | yes | L2 |
| `principal.id`, `resource.id` | raw; rewritten when the type ends in `Host` | only under A2 and A4 | L2 under assumption |
| `context` keys not in the key map | raw, passed through | yes | L2 |
| `context.host`/`name`/`domain`/`recipient_domain` | raw; host operation applied | only under A1 and A4 | L2 under assumption |
| `context.url_path`, `context.path` | raw; path operation applied | only under A1 and A4 — and a wrong guess flips outcomes | L2 under assumption |
| `context.currency`, `context.scheme` | raw; case operation applied | only under A1 | L2 under assumption |
| `entities` (caller-asserted) | raw in the input | yes, but whether they are consulted depends on the policy's `entities` setting | L2 |
| `entities` (store) | in the policy object, under the digest | yes | L2 |
| `kind`, `note` | raw in the input, dropped from the request | yes, under A3 | L2 under assumption |

The ragged edge is one column wide and every entry in it is the same word: the canonicalisation and
request-shape assumptions. Nothing about the Cedar grammar is the obstacle — the grammar is specified
and its engine is published. What is unspecified is the producer's own pre-processing, and it is
unspecified in this repository's `SPEC.md` rather than in Cedar's documentation.
